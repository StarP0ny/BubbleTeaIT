# BTI как координатор готовых движков

Режим включается разделом `[engines.cocoindex]` в машинном
`config-service.toml`. CLI и один stdio MCP обращаются к общему сервису BTI.
Сервис владеет отдельным runtime CocoIndex Code и отдельными индексами проектов.
Одна embedding-модель обслуживает все проекты этого runtime. Закрытие клиента
не останавливает движок; `bti service stop` завершает принадлежащие BTI процессы.
Пользовательские daemon других установок не используются и не останавливаются.

Явный `--config` выбирает указанный файл и имеет приоритет над автоматически
найденным машинным конфигом, включая явный выбор прежней конфигурации снимков.

## Установка

Основной пакет устанавливается с MCP:

```powershell
python -m pip install -e '.[mcp]'
```

Для CocoIndex Code нужен отдельный Python с закреплёнными зависимостями
`requirements/indexing-windows-py312.lock` / extra `[indexing]`: адаптер проверяет
`cocoindex-code==0.2.42`. Для `device='cuda'` нужен PyTorch с поддержкой CUDA;
CPU-сборка не становится CUDA-сборкой после изменения конфига. Веса устанавливаются
отдельно, автоматических скачиваний при работе BTI нет.

Serena и выбранный clangd/ccls также устанавливаются отдельно. Python мостика
Serena должен иметь MCP extra. Установка BTI создаёт `bti-language-server`:
он передаёт выбранному LSP аргументы, включая разрешённые GCC query drivers,
без shell и без изменений upstream.

Пример настроек — [config-service-engines.example.toml](../configs/config-service-engines.example.toml).
Модель, её точная ревизия, устройство и document/query prompt задаются явно.
Путь модели должен находиться внутри `models_dir`. Параметры prompt должны
соответствовать выбранной Sentence Transformers модели.

```powershell
bti --config C:/BTI/config-service.toml doctor
bti --config C:/BTI/config-service.toml service start
bti service config show
bti watch --list
```

Doctor проверяет установку и доступность CUDA без загрузки embedding-модели.
Status/list не запускают остановленный сервис и не загружают веса.

Флаги запуска имеют приоритет над файлом и видны в `engine_overrides`:

```powershell
bti service start --embedding-model E:/models/embeddings/model --embedding-revision EXACT_REVISION --embedding-device cuda
bti service start --symbol-server ccls --language-server C:/tools/ccls.exe
```

Также доступны `--embedding-python` и `--config`. Изменение пути модели требует
указания ревизии. Флаги не записываются в файл. Смена модели/движка, регистрации
проектов или workspace требует остановки и запуска сервиса; попытка такого
изменения файла видна в `config_error`, прежние настройки продолжают действовать.
Настройки poll/debounce/sync перечитываются. Изменения проектных `bti.toml`
подхватываются обычной сверкой источников.

## Проекты и точная выборка файлов

`projects.<name>.path` задаёт настоящий checkout, `project_file` — его `bti.toml`
или машинный конфиг компонента вне checkout. Все правила `include`, `exclude`,
`attach`, ignore, ролей и зависимостей обрабатывает существующий селектор BTI.
Для простого проекта можно вместо `project_file` задать `include`, `exclude`,
`attach`, `respect_gitignore` непосредственно в его машинной регистрации.
При явном `include` используется именно эта выборка; зависимости из находящегося
в checkout `bti.toml` автоматически к ней не добавляются.

Workspace может перечислять проекты явно через `projects=[...]`, либо сохранять
обнаружение `discover=['*/bti.toml']`. `default_project` выбирает основной проект
для поиска без селекторов. Без него при нескольких проектах требуется явный
выбор. Весь родительский каталог автоматически в корпус не попадает.

BTI создаёт постоянное служебное представление выбранных файлов в `data_dir`.
Только оно передаётся штатному индексатору: так сохраняются attach и границы
подключённых модулей, а движок не пишет служебные файлы в потребительские репозитории.
После индексации проверяются точное множество выбранных native-путей и число файлов.
Результаты отображаются на оригинальные пути и проверенные исходные строки.

CocoIndex Code сам выполняет нарезку, embeddings, инкрементальную индексацию,
хранение и ранжирование. BTI не объединяет внутренние базы и не применяет
собственный fusion поверх его выдачи. Между проектами выдача чередуется по рангам;
оценки разных индексов не сравниваются напрямую.

## CLI и MCP

```powershell
bti --project-dir C:/work/controller plan
bti --project-dir C:/work/controller sync
bti search 'Обработка ошибки датчика' --workspace work --projects controller reference --freshness wait
bti read --workspace work --project-name controller --path src/control.c
bti symbols --workspace work --project-name controller --path src/control.c --operation references --name controlTick
bti mcp --workspace work
```

В этом режиме MCP предоставляет `project_info`, `context_search`, `read_sources`,
`resolve_sources`, `list_files`, `code_symbols`, `watch_status`, `sync_status`,
`sync_project`. Агенту достаточно вызвать поиск или чтение известного пути;
предварительные переходы по каталогам и ID не обязательны.

В `coordinated-live` вызов `project_info` показывает область подключения.
Каждый результат `context_search` содержит `project`, `generation`, SHA файла
и готовые аргументы `next_read`. Передайте **весь объект** в `read_sources`.
Для совпадения внутри одной распознанной функции C/C++ это диапазон функции
(`context_kind=function`), в остальных случаях — соседние строки
(`surrounding_lines`). При очень длинной функции чтение вернёт следующий
`next_read`. Его `anchor_id` привязан к исходной версии в той же MCP-сессии.
После правки файла вернутся прежние строки и `source_changed=true`.
Для проверки текущего файла передайте путь и SHA без `anchor_id`.
`composition_id` нужен при явном выборе снимка через `mcp --snapshots`.

`plan` и `project_info` не запускают сервис или модели. Чтение известного пути
не требует готового vector index. Если сам сервис настроен на постоянный watch,
его фоновая индексация работает независимо от читающего клиента.

Поиск без `projects` использует основной проект. Для сравнения задаётся список
проектов; ответ сохраняет их имена, пути, строки и SHA. Ошибка одного поиска
возвращается в `omitted_projects`, а доступные результаты имеют `state=partial`.
Недоступный или частично построенный индекс не выдаётся за успешную пустую выдачу.
Лимит ожидания сверки общий для выбранных проектов.

В live-режиме `search` использует semantic channel. Для точной строки доступны
обычные `rg` и чтение исходников. `--channel text` в этом режиме отклоняется,
а не подменяется семантическим поиском.

## Обновления и версии

Watch использует существующую очередь BTI с polling и debounce. Стабильное
служебное представление позволяет штатному движку пересчитывать изменения
инкрементально. Повтор без изменений не вызывает индексатор. `freshness=wait`
запрашивает сверку байтов; `available` допускает прежнюю готовую версию с
состоянием актуальности. Если источник меняется во время индексации, проход
не публикуется и повторяется при следующей сверке.

Во время неуспешного обновления изменяемый native index не обслуживает поиск.
BTI не обещает атомарного переключения всей БД движка между версиями.
Хеши и содержимое исходников сохраняются отдельно: выданный evidence-ID
позволяет дочитать прежний фрагмент после правки файла. ID принадлежит MCP-сессии;
после перезапуска сервиса/истечения записи нужно повторить поиск. Для чтения
текущего пути можно передать `sha256`, чтобы отклонить устаревший locator.

Идентичность движка, модели, ревизии, параметров и локальной metadata модели
выбирает отдельный каталог индексов. Старые векторы не запрашиваются новой
query-моделью. Веса следует хранить неизменяемыми для заявленной ревизии.

Старый режим снимков сохранён для конфигураций без `[engines]`. Registry,
исторические индексы и явные CLI `--composition` продолжают существовать;
для их vector-поиска нужны прежние `[models]` и `[backends]` в машинном конфиге.
Новый live-индекс не является историческим immutable vector index.
Для прежнего MCP с 13 инструментами можно явно запустить `bti mcp --snapshots`;
основное подключение координатора от этого не меняется.

## Serena и сборка GCC

`engines.serena.server` выбирает `clangd` или `ccls`; сборку прошивки выполняет
её настоящий GCC/toolchain. `projects.<name>.compile_commands` указывает
реальную базу выбранной сборки. BTI сохраняет макросы и компилятор, адаптируя
пути к отдельному представлению файлов. Невыбранные generated headers остаются
в настоящих build-каталогах. Исходники и build-файлы потребителя не изменяются.

GCC-расширения могут требовать явных `remove_flags` / `add_flags` в регистрации
проекта. Эти изменения профиля показываются в результате. Они применяются
только к анализу, а не к сборке. Автоматической замены целевого toolchain нет.
Неизвестные response files требуют предварительно раскрытого compile database.

Повторные запросы используют одну Serena-сессию проекта. Изменение выбранных
источников, базы компиляции или профиля создаёт новую сессию, чтобы не возвращать
старые ссылки. Разные проекты не переключают общий active-project друг другу.
Serena получает только три инструмента чтения; операции изменения не доступны.

Результат показывает покрытие translation units, отсутствующие команды и
`build_verified=false`: наличие compile database не доказывает успешную сборку,
активность всех ветвей препроцессора или полноту ссылок. Ссылки могут указывать
на enclosing symbol или `file_context`; последний возвращает проверенные
строки файла и не выдаётся за точное место вызова. На проверенной целевой
GCC-конфигурации Serena с ccls вернула для определения строку сигнатуры, с clangd —
диапазон функции. Обе версии разрешали имена и в исключённой препроцессором ветке.
Активность ветки можно сверить с выводом целевого компилятора `-E`.

## Проверка установленного стека

```powershell
python tools/probe_engines.py --config C:/BTI/config-service.toml --compiler C:/toolchain/bin/gcc.exe --output .local/engine-acceptance.json
```

Проверка создаёт отдельные временные проекты и private service namespace,
вызывает настоящий stdio MCP и CLI, проверяет общий runtime двух клиентов,
add/edit/delete, прежний evidence-ID, перезапуск и повторную Serena-навигацию.
Потребительские checkout и рабочие индексы не используются. Временные результаты
и логи сохраняются для диагностики. GPU/веса и установленные движки нужны только
для этой явно запускаемой проверки; обычные unit-тесты их не требуют.
