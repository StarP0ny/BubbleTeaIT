# Сервис BTI, наблюдение и рабочие пространства

Сервис объединяет координатор синхронизации, очередь проектов и настройки
embeddings. CLI и stdio MCP используют один экземпляр на каталог данных.
Исходники проектов сервис не изменяет. Новые снимки и индексы хранятся в data_dir.

## Наблюдение за проектом

```powershell
bti watch
bti watch -p C:/work/controller
bti watch --list
bti watch --status -p C:/work/controller
```

Без `-p` берётся текущая директория. С `-p` / `--path` выбирается указанная
директория. В ней должен находиться `bti.toml`; watch не ищет родительский проект.
Существующий глобальный `--project-dir` также поддерживается, противоречащие
указания отклоняются.

Watch запускает сервис при необходимости, сохраняет регистрацию и возвращает
управление. Наблюдается выборка из конфига, включая зависимости. Закрытие
терминала не прекращает работу. Регистрации восстанавливаются после перезапуска.

```powershell
bti watch -p C:/work/controller --follow
bti unwatch -p C:/work/controller
```

Follow показывает изменения состояния; Ctrl+C завершает только просмотр.
Unwatch снимает ручную регистрацию. Если проект также подключён через workspace
или активный MCP-клиент, соответствующее наблюдение продолжает работать.
Снимки и индексы не удаляются.

Первый watcher использует периодическую сверку реальной выборки и хешей.
Файловые уведомления ОС пока не подключены. `poll_interval_seconds` задаёт
интервал проверки проекта, `debounce_ms` объединяет последовательные изменения.
`reconcile_interval_seconds` задаёт период обнаружения конфигов workspace.
Начальные значения — 1 с, 2000 мс и 60 с соответственно. Стоимость сверки больших
SDK отдельно не измерена; интервал можно увеличить.

Правки исходников, добавления, удаления и изменения конфигов приводят к новой
синхронизации. Готовые неизменившиеся units переиспользуются. Изменённый источник
может переиндексироваться целиком: пересчёт только изменённых строк не обещается.
Ignore, include/exclude и attach действуют как при ручном sync.

## Управление сервисом

```powershell
bti service start
bti service status
bti service config show
bti service stop
```

Status/list не загружают веса embedding-модели. Embeddings нужны для индексации
и смыслового поиска; генерация ответа моделью в этот процесс не входит.
Состояние остановленного сервиса отделяется от сохранённых регистраций.

Команды `service`, `watch` и `workspace` по умолчанию выводят читаемый текст;
`--json` меняет только формат. `search`/`read-source`/`list-*`/`symbols`
всегда печатают JSON. Логи процесса находятся в `runtime/service/service.log`
внутри data_dir. Обмен с сервисом идёт по защищённому токеном локальному RPC,
каталог runtime/service ограничен правами владельца. В Windows фоновый процесс
запускается через используемый BTI механизм WMI без окна.

Stop запрашивает завершение и ожидает выхода до 5 с. Уже начатое построение
снимка/индекса может завершаться дольше; до его выхода второй сервис не запускается.
Прерванный проход проверяется заново при следующем запуске.

## Настройки сервиса и embedding-моделей

Файл по умолчанию на Windows:
`%LOCALAPPDATA%/BubbleTeaIT/config-service.toml`. На системах с XDG_CONFIG_HOME:
`$XDG_CONFIG_HOME/bubbleteait/config-service.toml`.
Можно указать файл явно:

```powershell
bti service start --config C:/BTI/config-service.toml
bti --config C:/BTI/config-service.toml watch -p C:/work/controller
```

Все клиенты должны выбирать один data_dir, чтобы обращаться к одному сервису.
Пути внутри файла считаются относительно этого файла, `${NAME}` берётся из
переменных окружения. Пример: [config-service.example.toml](../configs/config-service.example.toml).

```toml
[service]
data_dir = '${LOCALAPPDATA}/BubbleTeaIT'

[paths]
models_dir = 'E:/models'

[sync]
enabled = true
debounce_ms = 2000
poll_interval_seconds = 1
reconcile_interval_seconds = 60

[embedding]
default_profile = "qwen06"

[embedding.profiles.qwen06]
backend = "qwen-dense"
model_path = 'E:/models/embeddings/Qwen/Qwen3-Embedding-0.6B'
python_executable = 'C:/BTI/embedding-runtime/python.exe'
device = "auto"
```

Путь Python в примере заменяется на установленный runtime с зависимостями
выбранного backend. Если его не указать, используется Python сервиса.
Модель должна лежать внутри models_dir и иметь действующий BTI manifest.
Конфиг не скачивает веса и не устанавливает ML-зависимости.

Поддержаны адаптеры `qwen-dense` и `cocoindex-code`. Стандартный рецепт Qwen
закреплён на Qwen3-Embedding-0.6B и ревизии, E5 — на multilingual-e5-small.
Другие модели не становятся поддержанными от изменения строки model_path.
`device="auto"` означает действующий режим адаптера; для закреплённого Qwen
это CUDA-профиль. Другие значения пока отклоняются.

Профиль по умолчанию выбирает рецепт новых индексов. Поиск существующего состава
использует его собственный рецепт; новую query-модель нельзя применять к старым
векторам. После смены default строятся новые units, алиас переключается только
после их готовности. Исторический поиск требует наличия совместимых весов/backend.

```powershell
bti service start --embedding-profile qwen06 --debounce-ms 1000 --poll-interval-seconds 3
```

Приоритет: defaults → файл → поддержанные BTI_* переменные → флаги запуска.
Переопределения флагами не записываются в файл и сохраняются при его перечитывании.
Повторный start с другими настройками требует сначала остановить сервис.

Сервис перечитывает свой конфиг автоматически. Ошибочная редакция сохраняет
прежние настройки и появляется в status. Смена data_dir требует перезапуска.
Старые пользовательский `config.toml`, `configs/bti.toml` и `.local/config.toml`
продолжают использоваться, если нового файла нет. Их не переписывают автоматически.
После появления нового машинного файла он становится авторитетным для сервиса;
нужные backend, пути и настройки symbols следует перенести явно. `service config
show` показывает эффективные настройки и список загруженных файлов.

## Workspace

Добавьте в конфиг сервиса:

```toml
[workspaces.example]
path = 'C:/work'
discover = ["*/bti.toml"]
exclude = ["artifacts/**"]
watch = true
```

Workspace обнаруживает проектные конфиги с учётом ignore и исключений. Все файлы
каталога автоматически в один корпус не попадают. У проектов сохраняются роли,
границы источников и точные версии общих модулей. Подключённая зависимость
не становится самостоятельным проектом без подходящего конфигурационного корня.
Конфликтующие имена проектов видны как ошибка.

```powershell
bti workspace list
bti workspace status example
bti watch --list
bti search 'Сравнить обработку ошибки измерения' --workspace example --projects alpha beta --freshness wait
bti mcp --workspace example
```

Watch=true включает постоянное наблюдение. Watch=false оставляет workspace
доступным для поиска: выбранные проекты регистрируются временно на время клиента.
Обнаружение новых конфигов выполняется периодически и при workspace-запросе.

## Прямой MCP

Проектное подключение совместимо с прежней командой:

```powershell
bti --project-dir C:/work/controller mcp
```

Первый запрос к проектному контексту подключает сервис. Предварительный
project_info и обход каталогов не требуются:

```text
context_search(query="Как измерение попадает в меню?", freshness="wait")
read_sources(requests=[{path: "trunk/Src/measuring.c"}])
resolve_sources(ids=["<ID из ответа>"])
watch_status()
sync_status()
```

Известный путь разрешается в whitelist снимка. Без source_id путь считается
от корня проекта, с source_id — от корня источника; допустим однозначный
абсолютный путь внутри объявленных границ. Без диапазона возвращается первое
окно до 120 строк. Для точного диапазона задаются оба start/end.

Обычный `freshness="available"` использует последний готовый состав и сообщает
состояние синхронизации. `freshness="wait"` ждёт проверки изменений до timeout_ms
(по умолчанию 30000, максимум 60000). При таймауте возвращается updating,
при ошибке — error; старые результаты не выдаются как свежие.
Изменение границ конфига блокирует неявную старую выдачу до обновления.
При sync.enabled=false автоматическое ожидание возвращает sync_disabled;
`sync_project()` и обычный CLI `bti sync` остаются явными способами обновления.
CLI `sync --recipe FILE` сохраняет прежний отдельный путь с общей блокировкой.
Обычный CLI sync ожидает завершения без общего лимита; `--timeout-ms` ограничивает
это ожидание. Ограничение 60 с относится к одному MCP/RPC-ожиданию, фоновое
построение после таймаута продолжается.

В workspace-подключении:

```text
context_search(project="alpha", query="Ошибка измерения")
context_search(workspace="example", projects=["alpha", "beta"],
               query="Сравнить обработку ошибки измерения", freshness="wait")
```

Выдача включает набор compositions, проектные привязки и потери покрытия.
Без projects выбираются все конфиги workspace. Поле compositions можно передать
обратно в context_search для закреплённого сравнения. Оценки разных embedding
моделей не сравниваются напрямую: результаты объединяются по рангам.
Общий бюджет ответа сохраняется, общие фрагменты могут иметь несколько projects.

Search/read уже выдают цитируемые IDs; resolve нужен только для метаданных.
Ссылки закреплены за снимками и переживают фоновую публикацию. Новое чтение
по пути выбирает новую готовую версию, чтение по ID сохраняет старую.
IDs разных проектов можно прочитать одним пакетом; две версии одного проекта
требуют отдельных вызовов. Перезапуск MCP завершает жизнь коротких IDs.
Явный composition_id сохраняет прежний режим точной версии.

## Проверки и ограничения

Изолированные проверки используют реальные снимки и детерминированный backend:
изменения файлов/конфигов, сохранение старого состава при ошибке, workspace-поиск,
закрепление версий и схемы SDK. Отдельно запускаются реальный фоновый сервис
и внешний stdio MCP-клиент с чтением по пути без discovery-вызовов.
Проверки сервиса не являются замером качества embeddings или индексацией
реального корпуса. В этом изменении продуктовые исходники и пользовательские
машинные конфиги не меняются. Настройки большого рабочего пространства и стоимость полных сверок
подбираются после отдельного измерения.
