# Проектные конфиги BTI

`bti.toml` описывает компонент и его источники. Приложение подключает конфиги
зависимостей; SDK и модули хранят правила рядом со своим кодом. Конфиг выбранной
Git-ревизии читается из текущего checkout, ничего не скачивается и не обновляется.

## Пример

В SDK:

```toml
schema_version = 1
[component]
name = "device-sdk"
kind = "sdk"
[source]
include = ["**/*.c", "**/*.h", "**/*.md"]
exclude = ["**/examples/**"]
[variants.mcu-v2]
include = ["Core/v2/**", "GPIO/**", "DMA/**", "README.md"]
```

В проекте:

```toml
schema_version = 1
[component]
name = "controller"
kind = "project"
[context]
product = "controller-v1"
configuration_status = "declared; active macros not verified"
[source]
include = ["src/**", "include/**", "CMakeLists.txt"]
role = "code"
[sources.requirements]
path = "docs"
include = ["requirements.md"]
kind = "documents"
role = "docs"
[dependencies.sdk]
path = "vendor/sdk"
variant = "mcu-v2"
```

`component.kind`: `project`, `module`, `sdk`, `documents`. SDK хранится как
отдельный module unit с ролью `sdk`. `source` — основной источник компонента;
`sources.<name>` — дополнительные источники с собственной папкой, ролью и
фильтрами. ID источника: `<component.name>.<name>`, для основного — `.source`.

Все пути считаются от своего файла. `dependencies.<alias>.path` указывает на
каталог с `bti.toml` или непосредственно на TOML-файл. Произвольный код не
исполняется. Неизвестные поля, отсутствующие зависимости, циклы, одинаковые
имена разных компонентов и конфликтующие выборы одного компонента отклоняются.
Одинаковое повторное подключение одного файла переиспользуется.

`include` — объединение POSIX glob-шаблонов; `*` — один сегмент, `**` — любое
число сегментов. Вариант и `dependencies.<alias>.include` добавляют пересечение
к базовому include основного `source`; `exclude` добавляется к исключениям.
Эти настройки не расширяют исходную выборку и не меняют дополнительные `sources`.
Вложенные конфиги не наследуют варианты родителя. Ветка может подключать свои
зависимости. Каталоги дочерних компонентов и вложенных источников автоматически
исключаются из охватывающих источников. Оставшиеся пересечения файлов — ошибка.

Git ignore включён по умолчанию, включая подключённые модули. `attach` явно
разрешает файл/поддерево внутри источника поверх ignore и автоматических
исключений; include, варианты и явные exclude продолжают действовать.
`attach = ["."]` разрешает весь корень источника, поэтому сначала ограничьте
его include/exclude. `respect_gitignore = false` отключает ignore только у
конкретного источника. `local` не добавляется в основной корпус автоматически.

## Запуск

```powershell
bti -h
bti plan --json
bti sync --json
bti project-info --json
bti list-sources --json
bti search 'Как отображается результат заводского теста?' --json
bti mcp
```

Поиск ближайшего `bti.toml` идёт от текущего каталога вверх и останавливается
на границе Git-репозитория. Изнутри сабмодуля выбирается его собственный конфиг;
для всего приложения используйте `--project-dir ROOT` или `--project-file FILE`.
Глобальные флаги задаются до подкоманды. Прежние `--project/--composition`
продолжают явно выбирать любой опубликованный состав.

`plan` не регистрирует источники и не загружает модели. Он читает выбранные
байты и показывает дерево конфигов с SHA, файлы, причины пропуска, пути/hash
правил ignore, не-UTF-8 и NUL-байты. Пустой источник и неподдерживаемый текст
делают план неготовым (код возврата 2). Маленький источник получает предупреждение;
один файл ТЗ допустим. Исключённый каталог показан целиком, его содержимое
не обходится ради статистики. Сводка не является измерением качества retrieval.

`sync` сначала проверяет весь корпус, затем регистрирует источники, создаёт
immutable snapshots и индексирует отсутствующие ready units. После готовности
всех индексов публикуются точный ID и удобный алиас проекта. Ошибка оставляет
прежний опубликованный состав; успешно построенные промежуточные units могут
переиспользоваться. Повтор без изменений сохраняет ID и не вызывает embeddings.
Изменившийся компонент получает новый unit; старый состав остаётся доступен.
SHA конфигов входит в метаданные состава. Исходное содержимое и embedding
recipe определяют возможность переиспользовать unit независимо от комментария
в конфиге. Постоянное наблюдение и параметры сервиса описаны
в [отдельной инструкции](service.md); установка Windows Service не требуется.

Для обычных CLI search/list/symbols состав берётся из найденного
конфига, если он опубликован и конфиг не изменился. Изменение рабочих исходников
не меняет закреплённый снимок: чтение сообщает `source_changed`. При включённом
watch/MCP автосинхронизация публикует новую версию; freshness=wait позволяет
дождаться её. Явный состав продолжает читать прежнюю версию.
Точный состав выбирается при начале команды. MCP `project_info` возвращает его
ID для последующих явных вызовов. Метаданные конфигурации не доказывают, что
платформа, варианты сборки и макросы соответствуют активной сборке. SDK можно
выбрать отдельно через
`source_ids` из каталога или `roles=["sdk"]`.

## Настройки машины и подключение агента

Порядок runtime-настроек: defaults → пользовательский конфиг →
`configs/bti.toml` проекта → `.local/config.toml` проекта → `BTI_DATA_DIR` /
`BTI_MODELS_DIR`. Пользовательский файл: `%LOCALAPPDATA%/BubbleTeaIT/config.toml`
на Windows, `$XDG_CONFIG_HOME/bubbleteait/config.toml` при заданном XDG_CONFIG_HOME.
Пути Python, весов, хранилища и endpoint задаются здесь, а не в компонентных
конфигах. Содержимое зависимостей не меняет runtime-настройки процесса.
Явные `--config` / `--local-config` сохраняют прежнее назначение.

Для существующей editable-установки launcher можно создать так:

```powershell
pwsh -NoProfile -File tools/install_cli.ps1 -AddToUserPath
```

Он использует `.venv` данного checkout и добавляет отдельный каталог launcher
в пользовательский PATH. Пакет и окружение должны уже существовать; перемещение
checkout требует переустановки launcher. Открытым терминалам и клиентам нужен
перезапуск для получения нового PATH. Для stdio MCP надёжнее указать абсолютный
Python executable, `-X utf8 -m bubbleteait --project-dir ROOT mcp`.

В проектном `AGENTS.md` достаточно указать `bti.toml`, когда использовать BTI,
и маршрут `project_info → list_sources/list_files → context_search/read_sources`.
Общий workflow описывается в проектном skill вне этого репозитория.
Описание tool и его опубликованная схема остаются источником точных аргументов.
